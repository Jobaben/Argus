# Orchestration / Supervision Layers for Coding Agents — State of Play (Sept 2026)

_Scope: the "Argus layer" — schedules, launches, isolates, verifies, retries, and reports on runs of agent CLIs (`claude -p`, `codex exec`, `opencode run`, headless `qwen`, etc.), in DAG/pipeline form with gates and checks. This is distinct from the underlying model quality._

## 2. Capability ranking, by how universal it is among the strongest layers

Ranked from "table stakes everywhere" to "still differentiating / rare":

1. **Isolation (container/VM/worktree)** — Present in essentially every cloud agent (Codex, Jules, Devin, Cursor, Copilot, Augment, OpenHands, Amazon Q, Replit) and is "load-bearing" for every OSS multi-agent tool (Claude Squad, Conductor, ccmanager, Gas Town all standardized on git worktrees in 2026). The only holdouts are pure orchestration frameworks (LangGraph/CrewAI/Mastra/n8n) that leave isolation to the deployment layer, and Aider, which works directly in the local checkout.
2. **PR as the terminal artifact / human merge gate** — Nearly universal end-state: every cloud/background agent produces a PR for review rather than pushing to main. Even OSS loop tools (Ralph, Symphony, Gas Town) converge on "agent works until a PR exists, human/CI merges."
3. **Repo-level memory files (AGENTS.md/CLAUDE.md and equivalents)** — Rapidly became a de facto standard: AGENTS.md is reported adopted in tens of thousands of repos and is now read natively by Codex, Copilot, Cursor, OpenHands, and Claude Code (which layers CLAUDE.md on top). This is the most "universal within 12 months" capability in the whole survey.
4. **Basic verification (compile/lint/test before declaring done)** — Common but the _rigor_ varies hugely: Devin/Copilot/Amazon Q/Replit run real test suites and (for UI) browser checks; Lovable/Bolt mostly do a shallow "try to fix" pass; pure CLI tools (Codex CLI, OpenCode, Claude Code primitives) only verify if the operator wires it in via hooks/prompts — it is not automatic.
5. **Retry / self-heal (feed failures back to the model)** — Almost every serious tool does _some_ version of this (Aider's lint/test loop, CodeRabbit's 3-attempt Autofix, Devin, Replit, Symphony's crash-restart, Temporal/Inngest's native retries). Bound and cap discipline, however, is inconsistent — few products publish a retry ceiling the way CodeRabbit (3 attempts) does.
6. **Planning/spec phase before code** — Now common in the frontier cloud agents (Jules requires plan approval, Devin plans first, Codex has plan mode, Copilot shipped Plan Mode in 2026, Factory has Spec Mode) but is still opt-in or absent in most lightweight CLI/OSS tools (Goose, ccmanager, Claude Squad don't impose one).
7. **Human approval gates** — Present almost everywhere as a _configurable_ control (Codex approvals, Jules plan approval, Copilot required review, Devin, orchestration frameworks' human-in-loop nodes) but enforcement defaults differ wildly — some ship "auto-approve after timeout" (Jules) which weakens the gate.
8. **Scheduling (cron/webhook/routine triggers)** — Increasingly available (Claude Code Routines, GitHub Copilot's issue-triggered agent, CodeRabbit's PR-triggered review, Symphony's continuous board-watching, Temporal/Inngest/n8n cron) but it is _not_ native to most CLI-first tools (Codex CLI, OpenCode, Aider, Goose) — they need an external cron/CI wrapper, which is precisely the gap a layer like Argus fills.
9. **Budget/turn caps** — Present as a knob in developer-facing tools (Claude Code `--max-turns`, Codex `--attempts`, Paperclip's budget enforcement, Temporal timeouts) but largely invisible/unconfigurable in consumer-facing cloud products (Lovable, Bolt, Replit expose "credits" rather than turn caps).
10. **Checkpoint/resume** — Solid in the durable-execution world (Temporal, Inngest, Mastra suspend/resume, Dagger caching, Gas Town's Beads) and in session-oriented CLIs (Claude Code sessions, OpenHands pause/resume) but weak-to-absent in many single-shot cloud agents and most lightweight multi-agent terminal UIs.
11. **Parallel attempts + selection (best-of-N)** — A 2026 differentiator, not yet universal: OpenAI Codex shipped a native Best-of-N feature; Ralph/Gas Town/Symphony achieve a looser version via many independent agents/hats; most other products (Jules, Cursor, Copilot, Devin) run one attempt per task and rely on retry rather than N-way sampling+selection.
12. **PR review-comment loop (address reviewer feedback automatically)** — Real but narrower: strongest in Copilot (re-trigger review → address → re-review), Devin, Ellipsis, and CodeRabbit's Autofix; largely absent as a first-class feature in CLI tools and pure orchestration frameworks, where it would have to be hand-built.
13. **Tracing/replay & evaluations** — Split cleanly along a line: purpose-built agent frameworks with an observability vendor behind them (LangGraph↔LangSmith, any OTel-instrumented pipeline↔Langfuse/Phoenix) have first-class tracing; most coding-agent _products_ only expose a session/task history UI, not exportable traces, and true evals (SWE-bench style pass/fail history per run) are essentially absent from consumer products and only appear in engineering-research contexts (OpenHands SDK's built-in eval harness is a rare product-level exception).

## 3. What the evidence actually supports, capability by capability

**Isolation.** Strong, consistent, and mostly _verifiable from documentation_ rather than independent testing (Codex's two-phase microVM design, Cursor's per-agent VM, GitHub's Actions-sandboxed coding agent, Augment's per-agent VM are all vendor-documented architecture, not third-party audited). Evidence quality: **vendor documentation, technically credible, not independently audited** — no public red-team report was found confirming these sandboxes hold under adversarial conditions.

**PR-as-output / human merge gate.** This is the one place independent evidence and vendor claims converge and _diverge sharply on outcome rates_: Cognition's own SWE-bench technical report claimed 13.86% end-to-end resolution (vs 1.96% prior SOTA) — published with an open GitHub methodology repo (`CognitionAI/devin-swebench-results`), which is better evidence discipline than most vendor claims, but Devin's later marketing (a "PR merge rate" of 67% in 2026, up from 34%) was contradicted by an independent Answer.AI test that found only a **15% success rate across 20 real-world tasks**. Evidence quality: **contested — self-reported benchmark with open methodology, but independent field testing shows a large gap between vendor and real-world numbers.** Treat any single vendor's "success rate" or "PR merge rate" as vendor-claim-only until replicated.

**Memory files (AGENTS.md/CLAUDE.md).** Adoption counts (reports of AGENTS.md in the tens of thousands of repos) are a real, checkable signal (searchable on GitHub), making this one of the better-evidenced convergence claims in the survey, even though no controlled study measures the productivity effect of having one. Evidence quality: **adoption data is solid; causal value ("does it make agents better") is anecdotal only.**

**Verification / retry loops.** The clearest _mechanistic_ evidence is Aider's own polyglot benchmark methodology: it explicitly scores the model "inside Aider's real edit loop," giving the model a second attempt using the failing unit-test output — this is a transparent, reproducible harness (also tracked independently by Epoch AI), so the marginal value of a test-feedback retry loop is about as well-evidenced as anything in this space. Evidence quality: **good — reproducible, third-party-tracked benchmark (Epoch AI), though it measures one product's loop, not the general claim.** Screenshot/browser verification (Replit's Playwright-based self-testing) is vendor-blog-documented with concrete before/after framing (claimed 3x faster / 10x cheaper than "Computer Use" models) but not independently benchmarked. Evidence quality: **vendor claim only.**

**Planning/spec phase.** No independent study isolates the effect of a plan-approval step on outcome quality; all evidence here (Jules plan approval, Devin plan, Codex plan mode) is vendor UX documentation. Evidence quality: **vendor claim / design description only.**

**Scheduling / continuous orchestration at scale.** OpenAI's own account of Symphony (built to escape the "3–5 sessions is the human attention ceiling" problem, reportedly producing a 500% increase in landed PRs on some internal teams) is a **single-vendor, unaudited internal metric** — striking if true, but not independently verified and not broken out by team size or task type. Evidence quality: **vendor claim only, treat 500% figure with caution.**

**Best-of-N / parallel attempts.** The technique has real research backing in the ML literature generally (best-of-N sampling with a selector improves pass rate, as shown across several 2026 arXiv papers on generative selection), which supports it as a mechanism, but no independent third party has benchmarked _OpenAI Codex's_ specific Best-of-N feature against single-attempt Codex on a fixed task set. Evidence quality: **mechanism well-supported in the literature; product-specific lift is vendor claim only.**

**Leaderboards (SWE-bench, Terminal-Bench).** These are the best _externally graded_ signal available, but need heavy caveats: SWE-bench Verified/Pro scores are frequently cited (e.g., "Fable 5 leads at 95.0%," Terminal-Bench 4.0 showing Codex and Claude Code statistically tied at ~58%) and are run by third parties, which is a real strength — but multiple 2026 papers explicitly argue these benchmarks are "misaligned with agentic software engineering" and can be gamed or overfit, and they benchmark the underlying model+harness pair, not the supervision/orchestration layer itself (a DAG scheduler wrapped around a weak model doesn't move these numbers). Evidence quality: **best available third-party signal, but a proxy — doesn't measure orchestration-layer value directly, and known to be contested/saturating.**

**GitHub stars / OSS adoption as a signal.** Explicitly a _weak_ signal, and this round of research turned up a cautionary case: Paperclip reportedly hit 38,000 GitHub stars in under four weeks — a "fastest-growing" claim that reads as hype-driven virality rather than validated usage, especially since star velocity has been repeatedly gamed in the AI-tooling space in 2025–2026. Compare OpenCode's reported 208k stars/16M monthly developers, which is a larger, longer-running number and thus a somewhat stronger (but still self-reported) adoption signal. Evidence quality: **weak, directional only; use relative trajectory, not absolute counts, and discount sudden spikes.**

**Independent developer-productivity evidence (the most important caveat for the whole space).** The METR 2025 randomized controlled trial is the strongest methodological evidence in this entire survey — a true RCT (the "gold standard," per multiple summaries) — and it found that experienced open-source developers using AI coding tools (Cursor + Claude 3.5/3.7 Sonnet) on real tasks in large (~1M LOC) repositories were **19% _slower_**, while believing themselves to be 20% faster. This doesn't directly indict _orchestration/supervision_ layers (the study used interactive, human-in-the-loop assistance, not headless scheduled pipelines with automated verification gates), but it is essential context: it shows that self-reported speed and vendor narratives about AI coding productivity have a demonstrated, measured gap from ground truth, and it should raise the evidentiary bar for any orchestration vendor's unverified productivity claim (e.g., Symphony's "500% more landed PRs," Devin's merge-rate figures). METR itself announced in Feb 2026 that it is revising its experiment design, implying even the RCT's own authors see measurement of AI-driven dev productivity as unsettled. Evidence quality: **strongest in the survey (RCT), but scope-limited to interactive assistance, not headless orchestration — extrapolate the caution, not the number.**

**Observability/tracing interoperability.** The claim that OpenTelemetry GenAI semantic conventions + Arize's OpenInference let Phoenix and Langfuse read each other's traces is a **verifiable technical/standards claim** (OTel is a real CNCF-adjacent open spec, and cross-tool trace portability is a testable property), making this one of the more solid "the ecosystem is converging" claims here, distinct from a vendor's own performance marketing. Evidence quality: **good — standards-based, independently checkable.**

## 4. What this means for a layer like Argus

The matrix suggests the highest-leverage, still-underserved capabilities for an orchestration/supervision layer sitting above `claude -p` / `codex exec` / `opencode run` are exactly the ones marked weak or "Ext" across most rows: (a) **scheduling of headless CLI runs** (only a handful of products do this natively — Claude Code Routines, Copilot's issue trigger, CodeRabbit's PR trigger — everything else needs an external cron/CI wrapper); (b) **enforced, visible retry/budget ceilings** (most tools retry informally with no published cap, unlike CodeRabbit's explicit 3-attempt bound or Temporal's timeout semantics); (c) **cross-CLI parallel-attempt-and-select**, which today exists natively only inside single vendors (Codex Best-of-N) rather than across heterogeneous agent CLIs; and (d) **portable tracing/replay** for headless agent runs, which currently requires bolting on Langfuse/Phoenix/OTel manually rather than getting it out of the box. Independent, rigorous evidence (METR RCT, Answer.AI's Devin test, the "benchmarks are misaligned" papers) consistently counsels treating any vendor's own success-rate or productivity number as provisional until replicated — which argues for an orchestration layer that logs and grades its own runs against verifiable checks (tests/lint/typecheck passing, not self-reported "done") rather than trusting agent self-assessment.
